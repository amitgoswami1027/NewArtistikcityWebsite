# Going live (general availability)

This is the one-time switch from "testing on the AWS site" to "open to the public". Everything that was on the live
site before is treated as test data: it is replaced by a clean starting point, and a single final snapshot keeps it
recoverable.

## What the reset does

`GO-LIVE-RESET.bat` (= `GO-LIVE-RESET.ps1`, run on your PC with the AWS CLI) does, in this order:

| Step | What happens | Undo |
|---|---|---|
| 1 | RDS snapshot `pre-go-live-<time>` of the live database, waited for until ready | this snapshot **is** the undo point |
| 2 | Database rebuilt through a private Session Manager tunnel: `schema.sql`, then `database/golive/golive-seed.sql` | restore the snapshot |
| 3 | Uploaded files in S3 (`storage/uploads/`, `private/`) **moved** to `archive/pre-go-live-<time>/`; the sample course files uploaded; CloudFront `/storage/uploads/*` invalidated | move them back |
| 4 | App restarted (`docker restart artistikcity` through SSM) and `/healthz` checked | - |
| 5 | Every other **manual** RDS snapshot in the region and every **retained** automated backup (of deleted databases) deleted, after you type `DELETE` | none |
| 6 | The live database's automated backups cleared: retention 0, then back to what it was (two short database restarts) | none |

Kept across the reset: the Configuration Panel values (`config_overrides`: payment, SMS and Google sign-in keys, still
encrypted) and the site settings (texts, SEO, contact, social links, header menu, cookie banner, page texts, landing
defaults, shop and offer rules). Removed from them: the admin "Site under construction" password (unless
`-KeepSiteLock`), simulated Razorpay and simulated sign-in codes, the shop's simulation mode (back to "test buyers only"),
values pointing at archived files, and the demo seed's placeholder phone / misspelt e-mail.

What the database holds afterwards (`database/golive/golive-seed.sql`, generated by `build_golive.py`):

* **one super admin** (every right), e-mail and name from `-AdminEmail` / `-AdminName`; you type the password
  (12+ characters). Set up two-step verification at the first sign-in (account menu > Two-step verification), then
  consider Settings > "Require two-step verification for all staff".
* **one student** `student@artistikcity.com` (verified, marked *test buyer*, so its checkouts can simulate payments);
  you type the password (8+ characters). Untick "Test buyer" in Admin > People when you no longer need it.
* **six sample courses** (4 live courses, 2 workshops) with every field filled: texts, highlights, outcomes, age group,
  level, dates (10-42 days ahead), prices, two photos, a trailer, a schedule PDF, 3 modules x 2 lessons each with notes
  (PDF) and a video, a task per module and a final project. Photos are the studio's own artworks; videos and PDFs are
  plainly labelled samples. **Prices, dates and texts are placeholders**: edit them, or hide the courses, in
  Admin > Courses before announcing anything.
* the reference lists (mediums, genres, levels, course types, categories, age groups, room scenes, print prices) and the FAQ.
* nothing made up: no orders, reviews, testimonials, paintings, stories or students' work.

After the restart the showcase landing pages are created again (`/landing/how-it-works`, `/landing/commission` and a
landing page for "Watercolour Landscapes for Beginners"), so there is one landing page to test checkout with.

## Run it

1. Deploy the current release first (push to `main`, GitHub Actions deploys and runs the migrations), so the database
   has every table `schema.sql` knows.
2. On your PC, in the project folder, with the AWS CLI signed in and the Session Manager plugin installed, and
   `START-ArtistikCity.bat` run once (it downloads the MySQL client and Java and builds the jar):

   ```
   GO-LIVE-RESET.bat -DryRun
   ```

   It lists the website, the database, the number of files in S3, every manual snapshot, the automated / retained
   backups and the server settings, warns about anything that still says "testing" (`PAYMENT_TEST_MODE`,
   `AUTH_EXPOSE_DEV_OTP`, `SITE_PREVIEW_PASSWORD`, missing `MAIL_HOST` / `OTP_SECRET`) and changes nothing.
3. Fix the warnings (delete the parameter in Parameter Store and redeploy), then:

   ```
   GO-LIVE-RESET.bat -AdminEmail you@yourdomain.com -AdminName "ArtistikCity"
   ```

   Type the two passwords (twice each; only bcrypt hashes leave the program), `GO LIVE`, and later `DELETE` for the
   old snapshots. It takes 15-30 minutes, most of it waiting for the snapshot and the backup restarts.
4. Rehearse first if you like: `GO-LIVE-RESET.bat -Local` does steps 2-3 on your PC's own database (no AWS at all).

Options: `-KeepSiteLock`, `-KeepOldSnapshots`, `-KeepAutomatedBackups`, `-SkipS3`, `-Region`, `-Stack`.

## After the reset

- [ ] Sign in at `/admin/login`, set up two-step verification.
- [ ] Admin > System parameters > Configuration Panel: Razorpay **live** keys (and PayPal), SMS provider, Google sign-in.
      The reset prints which keys were kept.
- [ ] Admin > System parameters > SEO & Layout Controls: contact e-mail / phone / address, the Our vision, Instructor,
      Customer support and FAQ tabs.
- [ ] Admin > People: add the instructors (they appear on `/instructor` once chosen in the Instructor tab).
- [ ] Admin > Courses: real prices, dates and texts for the sample courses, or hide them and add your own.
- [ ] Buy a course as the student with "Simulate payment", open the lesson, then one real small payment with your own card.
- [ ] Admin > System parameters > Site Access Password: off (the reset already removes it unless `-KeepSiteLock`).
- [ ] `https://<your domain>/robots.txt` allows crawling and `/sitemap.xml` lists the courses; submit the sitemap in
      Google Search Console.
- [ ] Delete the `pre-go-live-<time>` snapshot and the S3 `archive/` folder once you are sure you won't need them
      (a manual snapshot costs storage until deleted).

## Notes

- RDS can't delete a running database's automated backups one by one; turning backups off deletes them all, and changing
  the retention from or to 0 restarts the database ([AWS: backup retention](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html),
  [deleting retained backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups-Deleting.html)).
  The reset turns them on again right away, so point-in-time recovery restarts from the clean database.
- Tables on the server that `schema.sql` doesn't know are listed and left alone.
- Tests: `tests/system/test_golive.py` checks a reset database end to end (production profile); the reset itself was
  exercised with a stand-in AWS CLI that records every call.
